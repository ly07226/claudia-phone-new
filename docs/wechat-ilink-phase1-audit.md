# 微信 iLink / ClawBot 接入：阶段一架构审计（初版）

状态：独立分支上的设计与静态审计；尚未接入微信、未部署。此文档不是全仓审计通过证明。

## 已核对的现有实现

- `package.json`：React 19、Vite 6、Dexie 4；前端不是可常驻监听的服务器。
- `src/Chat.tsx`：已存在 `cloudIdentity` / `cloudFunctionRequest`，仅在云端身份配置完成后报告聊天前后台状态；不能假定用户默认登录。
- `src/generationTasks.ts`：现有生成任务是浏览器进程内 Map，依赖 `chatService` 和 Dexie；页面关闭后不可直接由 Supabase Edge Function 调用。
- `src/ChatHub.tsx`：日常聊天设置按 `characterId` 和 `mode='daily'`、空 `worldId` 查询，已有主动消息选项，但当前测试依赖前台运行；微信主动消息不能直接复用其发送渠道。
- `src/chatHubTypes.ts`：社交模块数据结构独立，不应误当作微信 iLink 消息结构。

## 外部实现依据

Float: `tools/weixin-local-assistant/README.md` 与 `docs/weixin-cloud-assistant.md`。其云端实现采用 Supabase Edge Function + pg_cron，复用本地助手核心；其文档明确提示冷启动离线丢消息、微信 token 失效需重扫、动态世界书关键词激活不完整等限制。这些是 Float 的实现说明，不能自动视为 Claudia Phone 的验证结果。

## 第一版架构决策（待代码验证）

1. 仅开发独立分支；禁止写入 main 或自动部署。
2. 接入模块必须独立于现有浏览器生成任务：微信事件 -> 服务端验证/去重 -> 绑定的角色/日常会话 -> 服务端生成适配器 -> 微信回执 -> 同步记录。
3. 先只允许绑定单个日常角色；不接入剧本世界、分支时间线和其他角色。跨世界功能必须单独设计和测试。
4. 微信凭证、Supabase service_role 和模型密钥只能放在服务端受保护存储；不能直接写入前端、Git 或导出备份。
5. 用户主动扫码并授权才创建绑定；解除绑定必须停止轮询、清理凭证及任务。
6. 不依赖单纯内存锁。按外部消息 ID 做持久化幂等；生成前抢占租约，发送后记录回执；对“发送成功但记录失败”的模糊状态禁止盲目重发。
7. 云端消息与本地 Dexie 同步要有可重放游标、身份作用域和冲突规则；禁止从云端直接覆盖本地聊天。
8. 第一阶段先文字双向消息，再研究图片、语音和主动消息；主动消息的权限与速率必须实测。
9. Supabase Edge Function + pg_cron 为优先验证方案，若 iLink 长轮询与平台执行时长不匹配，则转常驻 Worker；不预设任一方案已稳定。
10. 任何微信接口不可用、账号无准入、过期、限流都要显式反馈，不能静默模拟成功。

## 第二轮审计：已核对的关键阻断点

### 身份和云端接口
`src/cloudIdentity.ts` 使用可选的 Supabase 匿名身份，浏览器本地存储 session，`cloudFunctionUrl` 和 `cloudFunctionRequest` 目前只允许四个指定云函数名称。微信绑定接口需要单独扩展允许列表和鉴权；不能用匿名账号标识直接推定跨设备同一人，也不能默默为普通聊天创建账号。

### 聊天生成和一致性
`src/chatService.ts` 的 `sendMessage` 调用 `generate`，读取 Dexie、检查 timeline epoch、发送租约、角色 API 密钥，再通过 `buildContext` 组装提示词。它还处理角色心声、回复版本、消息路径和保存事务。服务端不能简单复用浏览器模块，也不能仅用角色 persona 代替完整上下文。

### 数据作用域
`src/chatTypes.ts` 的 Conversation 以 `scopeKey`、`characterId`、`mode`、`worldId` 定位会话；记忆 `memoryStore` / `memorySummary` 属于会话。Message 有独立 ID、variant、引用、编辑和归档字段。微信导入必须带来源 ID 和单独的远端映射，避免冲突与跨世界串线。

### 本地数据库
`src/store.ts` 的数据库是 Dexie v7；新微信绑定元数据最好先存在服务端，前端只持有不敏感的绑定引用。不得在尚未验证备份/恢复兼容性前新增 Dexie store 或修改版本。

### 新发现的高优先级风险
1. 浏览器本地 API credential 与角色世界书不自动存在于 Supabase：必须设计明确、最小化、加密的运行包同步，并在角色配置改变时失效/更新。
2. 微信云端回复与前端聊天同时进行时会产生顺序冲突；需要统一服务端消息序列、租约及客户端合并协议。
3. 匿名身份随设备清理可能丢失；绑定恢复和撤销需有可核验的所有权机制。
4. Float 的运行包同步方案不能直接复制，因 Claudia Phone 的心声、分支、记忆摘要与提示词预算均不同。
5. 在微信接入未验证之前，不应将世界书、聊天记录或 API key 自动上传云端。

### 下一步具体实现顺序
A. 审计 Supabase schema / functions 和已有云端同步协议；
B. 实现不含真实凭证的协议适配接口与类型验证、模拟 iLink 收发测试；
C. 安全绑定与扫码接口；
D. 服务端提示词/记忆等价性与持久消息同步；
E. 真机联调与可选云端定时运行。

## 产品范围决议：仅日常聊天（2026-11-16）

- 微信绑定入口仅放在日常聊天的角色设置，不放到世界管理、剧本、世界聊天设置中。
- 一个微信 Bot 绑定必须明确指向一个现存的 `mode='daily'` 且 `worldId` 为空的 `conversationId`，以及其 `characterId`；服务端在每次处理消息时复核绑定，不能只信任客户端传来的 ID。
- 不上传、不读取、不检索其他世界/剧本的对话、世界书、记忆、人物专属设定或时间线。若角色被删除或日常会话不再有效，自动暂停绑定。
- 微信同步仅针对该日常会话的当前有效路径。编辑、删除、重新生成时必须制定确定性冲突规则；首版优先文字。
- 初版按一个绑定一个日常角色实施；以后如需多角色需单独设计多 Bot 的身份路由，不能把多个角色混进同一会话。
- 该范围缩减并不消除云端身份恢复、凭证安全、提示词一致性、重复扣费及消息幂等风险。

## 产品验收更新：微信是日常聊天的第二入口

用户确认：微信用于不方便打开小手机时与日常角色聊天；微信收到用户消息后自动尽快回复；微信双方消息必须出现在小手机对应日常会话，且角色继续沿用该会话上下文。**不要求微信主动找人**。

### MVP 必须实现
1. 用户明确授权扫码绑定一个日常角色。
2. 微信收到文字消息 -> 可靠地入库 -> 调用该日常角色的模型和上下文 -> 将回复发回微信。
3. 微信用户消息和角色回复同步到小手机同一日常会话；本地重新打开也能拉取，不生成第二份重复消息。
4. 小手机发出的消息更新服务端同一会话的上下文；微信后续回复能看见这些消息。是否将小手机发出的消息反向推送到微信，须单独验证协议是否支持，不能混同于上下文同步。
5. 角色配置/记忆同步需经过显式授权，保证顺序一致、删除/编辑冲突可处理。
6. 未连接、授权过期、服务异常、同步失败时明确显示状态；不得假称消息已送达。

### 明确不在 MVP
- 角色主动发起微信消息、定时问候、概率触发、朋友圈、世界聊天、剧本聊天、语音图片、多个角色共享同一微信机器人。

### 延迟与交付语义
- “立即回复”是体验目标而非硬实时承诺；分别测量微信入站延迟、模型生成耗时、微信出站延迟和本地同步延迟。
- 对外展示状态区分：已接收、生成中、发送中、已确认发送、同步失败。发送结果不明时不能自动无限重试。
