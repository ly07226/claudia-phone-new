# Issue #81：原始聊天历史召回审计与验收

## 范围及基线

基于 `origin/main` `67314de7595301440c30803f8361f333f7235aca`，独立分支 `feat/raw-history-recall-81`。不合并 main，不部署 Production，不调用付费模型。未修改记忆总结格式、用户配置、数据库版本、人物设定、聊天 UI/CSS、Story 或游戏。原工作树的 137 项未提交/未跟踪成果保留；工作在独立 worktree。

## 原始调用链与确定性问题

`chatService`/生成任务 → `buildContext` (`src/chatContext.ts`) → `activeMessages` (`src/messagePath.ts`) → `resolveTimelinePath`/`nodesForHead` (`src/timelines.ts`) → 最近 30 条、世界书、`memoryContext` → 现有 Provider → 现有消息提交。

1. `chatContext.ts:17,48,65` 保留最近约 30 条（另有 24000 字符总预算），窗口外的原话没有独立检索通道。`memoryContext.ts:31–47` 长期记忆依赖已保存标签；`memoryMagnetRecall.ts:5–15` 主要是标签字面命中。自动总结被拦截或积压时，未产生对应摘要/标签，旧原文不会自然进入最终请求。基线三个实际发送测试失败：下午经期→晚上身体不适、五天前不婚态度→婚姻、总结失败130轮积压→原始事件。这证明漏传前情，不代表已证明真实模型看到正确前情后一定遵循。
2. `timelines.ts` 原先每个新事务重新载入并校验整条不可变路径；超过 20000 节点又回退逐节点读取，普通追加再做全量投影协调。数据仍完整，但发送成本随历史增长。基线 30000 条模拟发送/保存耗时 21863ms、150010 次 SHA；原文召回缺失。
3. 缓存不能只靠延迟广播作安全依据：开发中双标签页同 ID 改写来源并正确更新指纹，曾复现旧证据被重用。已新增保守读取屏障，并用该失败用例验证修复，未放宽来源校验。

## 实现

### 独立原始证据索引

- `rawHistoryTerms.ts`：本地中文双字/英文词 + 小型可维护主题同义集合；经期/例假/生理期、结婚/婚姻/领证等关联。不是远程 embedding，也不承诺理解所有同义句。
- `rawHistoryRecall.ts`：按数据库、会话、角色、Daily/World、worldId、时间线及 epoch 隔离；仅索引已验证有效路径。冷建索引分片让出主线程，正常追加只索引新行，主题倒排列表二分定位、有限候选排名。
- 0–3 天提高优先级；4–14 天相关主题召回；更早仅明确偏好、约定、共同经历等耐久信息。较新明确态度优先。窄泛问候可关联近期重要用户事件；明确无关话题不注入旧身体状态。
- 不确定、假设、玩笑保守排除；保留原说话人、原时间和 messageId。不将旧身体状态断言为现在仍持续。计划不等于完成，角色发言不等于用户事实。
- 短原话完整引用，长消息只取连续原文片段并标 `partial`；不改写/拼接事实。将历史 JSON 明确标成资料而非指令，转义标签边界。语义/提示注入防御并非数学保证，模型最终质量仍需实测。
- 最多 4 条、96 候选、单引文 600 字符、整个块 UTF-8 字节成本不超过 3000，并继续受现有系统字符余量约束；UTF-8 字节是保守代理，不是假称精准模型 tokenizer。保留现有近期原文、世界书/人物预算与 API 参数。
- 最多两个会话的易失索引，每个至多 50000 条 / 8,388,608 个 UTF-16 正文代码单元（不是 heap 字节上限）；达到上限标记 trace.incomplete，**不删除原始数据**。没有新表、没有升级 Dexie，无导出格式变化。

### 完整性与性能

- `pathProvenance.ts` 给已验证请求快照附加 WeakMap 证明；`messagePath.ts` 的历史前缀截取同步缩短节点证明，防止重生成使用未来信息。
- `timelineReadCache.ts` 只在事务成功提交后发布验证前缀；节点变更、删除、事务中改写、关闭/重开、恢复使证明失效；回滚不能发布信任。新节点仍校验指纹，保留所有归属/祖先/重复/断链检查。
- `timelines.ts` 新增仅适用于普通单调追加的快速路径：已提交投影证明 + 当前事务新建消息 ID + 数据库索引 count + 版本归属/元数据一致性。编辑、归档、重生成、未知来源、乱序一律使用原完整协调。修复追加的 variant.userEdited 元数据与旧路径不一致，ZIP 全库校验通过。
- `chatSourceReadBarrier.ts` 复用现有只读 Service Worker 客户端清点协议。只有确认同源单窗口、同一 worker 时跨事务重用缓存；多个窗口/未知/超时保守全读。不能把 Dexie 广播送达时间当成强一致性。没有新增网络或 LLM 调用。
- 冷读取仍需现有完整路径快照，热路径仍有数组/副本 O(N) 成本；**不能宣称整个聊天管线完全 O(1) 或首次无卡顿**。原始召回本身不在每次热查询重新扫描全部正文。

新版本三次热构建均 0 次历史 SHA，追加/后续上下文 1 次新 SHA，正常发送新用户+回复 2 次 SHA；30k 基线三次热构建累计90000次，模拟发送150010次。三个大小均成功召回原文、只发出1次模拟请求，并实际保存 N+3 条原始消息。

修复版本 fill 输入测量分别64/128/237ms，这是一次 Playwright fill 墙钟时间，不是逐键交互延迟分布。30k基线曾在进入聊天后5秒内找不到输入框，故**没有基线30k输入耗时**；模型调用/保存阶段数字取自已记录的 evaluate 返回追踪，不将该基线 UI 用例记为通过。最终这次测试三个规模的冷构建均变慢，新增索引有成本，需明确披露；多窗口/无ServiceWorker保守模式及大规模 World 记忆注入性能尚无独立基准。

## 限制与后续验收

- 无真实 iPhone Safari/standalone PWA、后台恢复、中文输入法或低内存设备验收，390/430px 仅 Chromium 浏览器模拟。截图在本地 `/tmp/recall81-mobile-{390,430}.png`。
- 无真实付费模型测试；证明请求含正确原始证据、作用域/保存不退化，不能证明角色100%自然引用或不会语义误判。
- 本地同义词/重要性/不确定性判断是有界启发式，可能漏召回、保守过滤；4条有限预算也不能保证覆盖所有历史。单条长消息最多256词项，未覆盖主题仍可能遗漏；超出50k/8,388,608字符索引容量标不完整，需后续磁盘索引方案，不能隐瞒。
- 首次读取约4.73s/30k仍可感知，内存峰值未取得可靠 heap 指标；数据隔离优先于性能，不启用多窗口盲目信任。
- 易失索引不进入备份，恢复/刷新后重建。旧v8数据/指纹/ZIP协议不变，无用户历史/配置删除、迁移、重写。
- 人物设定、World归属、原始消息与API配置保持原有权威；没有新增付费请求、摘要任务或隐式重试。实际模型输入可增加最多该3000字节代理预算。
