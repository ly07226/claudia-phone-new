## 当前机制与兼容策略

- 原始消息、不可变路径、回复版本仍由原系统保存；记忆条目、修订、摘要凭据与检查点仍嵌在 Conversation 中，没有另建记忆系统。
- 模型输入使用有预算的核心记忆、相关长期记忆、有效组摘要及有效自然日摘要；保存全部历史不等于每次把全部历史发给模型。
- 新摘要使用 `s3:` 来源指纹（消息、有效文本、版本、附件 ID）。旧五字段指纹仅在不可变原始路径可证明与当前来源一致时兼容；原凭据不覆盖。
- 无法核验的旧记录仍完整保留、可查看和编辑，不伪造来源，也不静默收费重建。旧自动记忆缺少来源绑定时显示说明，用户可通过编辑确认生成新的手动修订；旧修订保留。
- 来源改变或分支/epoch 失效的派生事实不进入新请求。已处理旧轮次发生编辑/重新生成时，自动入口不再把它们计为新轮次；主动确认才重建，正常新增轮次继续按间隔处理。
- 旧二级摘要保留所有版本；未核验旧日期不自动重建。失败窗口及恢复检查点需主动继续，不能因唤醒重复发起请求。
- 单轮长文本可分片，所有原文按顺序保留。一个逻辑组全部成功才提交一张凭据。超过 100 分片的输入在请求前拒绝，未丢弃原消息。
- V2 分支原本已使用 Dexie v8（新增 summaryLeases）；本轮没有再升版本。备份继续使用现有 ZIP/加密协议及 20 张持久化表的 v7/70 档案结构，临时租约不导出。支持旧备份进入 V2；这不表示旧客户端能使用所有新增 V2 字段。

## 大容量实测及性能边界

环境：Linux 桌面 Chromium，Playwright iPhone 13 视口；单 worker；合成隔离数据库，无真实用户内容。不是 iPhone 硬件，也不是 Safari。

| 操作 | 最终实测 |
| --- | ---: |
| listMemories（20k 修订） | 205.4 ms |
| summaryStatus（5k 凭据） | 3278.0 ms |
| 读取路径并组装记忆上下文 | 2940.8 ms；成功注入 12 条、约 1192 估算 Token |
| UI 进入含 10k 消息的会话 | 7182 ms |
| 输入测试草稿串 | 1443 ms |
| 实际挂载消息行 | 10000 |

大容量测试首次暴露 PrematureCommitError；中间保活试验读上下文约 62 秒后失败为空；最终修复成功。**这不是原始提交与最终提交的受控 A/B 跑分，不能声称某个百分比的性能提升。**
这些数字表明当前分支的大数据性能仍不足。不能把提高容量常量等同于已具备良好 iPhone 性能。main 已有聊天窗口化等修复，但本轮没有擅自整合。记忆和凭据仍嵌入大 Conversation，存在克隆/校验/序列化成本；新增摘要还会追加修订。删除记忆保留 tombstone，因此不等于释放修订容量。

## 剩余风险与验收边界

1. **必须先完成最新 main→功能分支的受控整合验收，再考虑合并发布。** 尤其 main 改变了有效文本规范化，来源指纹兼容测试需要覆盖规范化前后的旧摘要；当前 s3 不能被当成覆盖未来所有规范化变更的保证。
2. 大容量读取和输入仍慢；20k 修订/5k 凭据的安全上限不是可扩展存储设计的证明。本轮未实施分表迁移、压缩或删除。
3. 备份仍有单条记录等原安全上限。接近 10M 中文字符的嵌入记录可能超过单条备份上限；本轮没有用删内容规避，也未宣称极限容量备份已经解决。
4. 没有可靠来源的旧自动事实需要人工确认，保留但不自动注入；已核验的历史事实也不等于永远适用于当前现场。没有宣称能自动理解所有自由文本中的过期、关系变化或跨片条件。
5. 摘要输入目前不理解图片内容，只包含附件数量/来源 ID；不能声称自动识图。
6. 长输入的 V2 分片和组摘要合并可能产生多次付费调用，界面已明确说明；本轮测试未付费。不能保证已经发出的请求取消后服务商不计费；只保证不静默无限重试。
7. iOS 后台挂起、真机多标签/存储压力、真实模型质量尚未验收；模拟视口测试不能代替这些验证。
8. 非标准/损坏来源的旧数据与所有历史组合尚未穷举；不会为了“通过”伪造来源或清空原记录。
